The system at three zoom levels — what it is, what it is made of, and what happens inside — plus the request flows and the data model that hold it together.

Zoom out and PoMiniGames is one box with a player in front of it and five outside services behind it. Zoom in and that one box becomes a browser app, a web host, two storage systems and a carefully metered AI pipeline. This page walks that zoom, then follows a single score from the player's fingers to the leaderboard and back.

// AFTER UseAuthentication on purpose: read any earlier, the principal is not yet established and
// every signed-in player would be charged to their IP — sharing one ledger with everyone behind
// the same NAT. After UseRateLimiter too, so a shed request never opens a scope at all.
app.UseAiUsageScope();

// CSRF gate. Deliberately AFTER UseAuthentication: the antiforgery token is bound to
// the user's identity claims, so validating before the principal is established would
// reject every token this same user was just issued. After UseRateLimiter too, so a flood
// of token-less writes is shed by the limiter rather than each one paying for a
// Data Protection unprotect.
app.UsePoMiniGamesAntiforgery();

How an AI call travels

The data model

There is no relational database here. Every table is an Azure Table: a PartitionKey that groups rows and a RowKey that names one. There are no foreign keys and no joins; relationships are expressed by choosing the same partition and by hashing the same fields into the row key.

Leaderboards are one mechanism, not thirteen. A game declares a HighScoreDescriptor<T> — the table, the partition, the fields that make up the row's identity, and how to rank it src/PoMiniGames.Infrastructure/Services/HighScoreDescriptor.cs:32. Changing the identity fields re-keys the board, which is why the existing rows keep their old row key and stop appearing on the new board.
