PoMiniGames User journeys and experience

User journeys

What a person actually does, from opening the site to their score appearing on a leaderboard — and what the machine does at each step.

Every journey on this page follows the same shape: the person does something in the browser, the browser asks the server for permission or for a fact, and the server answers. The games themselves never run on the server. The server's job is to be the referee and the record keeper, not the opponent.

These journeys are written from the code, not from a design document. Where a journey needs a number — a rate limit, a timeout, a ceiling — the number carries a file:line citation. Where the code does not declare a number, the page says so rather than inventing one.

Journey 3 — Play someone else, over the network

Online play runs over SignalR. Two shapes exist: a lobby hub that finds and seats players, and a play hub that carries the actual match or race.

  1. The lobby seats the players

    Each game owns its own lobby hub: Racer, Cabinet, Voxel Strike, Brawl, Couple Quiz and Fun Quiz all have one src/PoMiniGames.API/Infrastructure/EndpointRouteExtensions.cs:122 src/PoMiniGames.API/Infrastructure/EndpointRouteExtensions.cs:123 src/PoMiniGames.API/Infrastructure/EndpointRouteExtensions.cs:124 src/PoMiniGames.API/Infrastructure/EndpointRouteExtensions.cs:127 src/PoMiniGames.API/Infrastructure/EndpointRouteExtensions.cs:132 src/PoMiniGames.API/Infrastructure/EndpointRouteExtensions.cs:136.

  2. The play hub carries the match

    Cabinet's race hub sends a fresh race code every time so one results screen cannot pick up the next race.

  3. The server is the authority

    PoBrawl's match hub relays frame-stamped inputs and answers Ping for clock sync; snapshots go out at 10 Hz. The server decides which frame each input lands on.

  4. The result is recorded

    An online match posts its result to an authenticated endpoint. When the Elo write fails, the endpoint answers 503 with Retry-After: 5 and releases the claim, so a retry within 90 seconds still works.

  3. A refusal ends the story

    A payload the server rejects outright is dropped rather than replayed on every future flush; only entries that could still succeed stay queued.

  4. A double-submit is impossible

    Re-entrant flushes are ignored, so a startup flush and a reconnect flush cannot submit the same score twice.

What every journey has in common

The game is never on the server

Engines load on demand from wwwroot/js/ and run in the browser. The server sees scores, not keystrokes, for a solo run.

Two tokens, always

A bearer token says who you are. An antiforgery token says the request really came from your signed-in browser.

Free paths are not fallbacks of last resort

They are the default. The paid paths are additions on top, and the app behaves identically without them.

Failures are legible

A refused score names its reason. A refused write names its reason. A storage outage degrades the leaderboards instead of the games.
