PoMiniGames Executive and plain-English overview

PoMiniGames

A website with thirteen small games on it, where the games run entirely in your browser and the server mostly keeps score, referees multiplayer matches, and — only if you ask it to — borrows a little intelligence from a cloud AI model.

Think of a funfair with thirteen stalls and one ticket booth. The games themselves are the stalls: you walk up, play, and walk away. The booth is the server. It does not play the games for you; it hands out tickets (your sign-in), keeps the high-score book, and referees the online matches so nobody can claim a win they did not earn. The AI is a paid extra at two stalls — if you never switch it on, you never pay for it and the games still work.

Who it is for

The player

Signs in with a Microsoft account, plays a game in the browser, and sees their score land on an all-time or this-week leaderboard. Nothing has to be installed — the app is a Progressive Web App, so it can be added to a phone's home screen and it keeps working when the network does not.

The operator

Wants the site to cost nothing when nobody is playing it. Free App Service tier, free Table Storage, and every paid AI call behind an opt-in, a daily per-player token ceiling and a server-side switch that can be flipped off without a deploy.

The five ideas behind the code

Most of the architecture falls out of five decisions. Each one has an everyday equivalent that makes the rest of the documentation easier to read.

Analogy
Middleware → a security checkpoint on the way into the building — you pass through it before you reach the room
Analogy
Dependency injection → a central supply closet — each part of the app asks the closet for what it needs instead of building its own
Analogy
Database and Table Storage → a digital filing cabinet — one drawer per game, one card per player, and every card has an address
Analogy
API endpoints → the order counter — you ask for something specific by name and get one specific answer back
Analogy
JWT token → a visitor badge — it says who you are and when you got it, and nobody has to check a list
Those five metaphors are used consistently throughout the suite. The house rules this app lives by

The browser is the game

The client ships as a trimmed WebAssembly bundle, so every DTO it exchanges with the server needs a source-generated JSON entry src/PoMiniGames.Client/Services/Http/ApiJsonContext.cs:20.

One origin, no CORS dance

The host serves the client, so production has no cross-site setup. The development CORS policy exists only for the local split-port setup src/PoMiniGames.API/Program.cs:228.

No database

There is no SQL anywhere in this app. "A player" is simply whoever the sign-in token says they are; there is no Player table src/PoMiniGames.Infrastructure/Services/StorageService.cs:24.

Warnings are failures

The build treats every warning as an error, so a change that produces one does not reach the branch.
