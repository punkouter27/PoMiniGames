Identity & Security Report

In plain English: There is no sign-in. Each browser makes up a random player id and remembers the player's three initials; the server uses them to label scores. Every write request is still checked at three gates: Anti-Forgery (CSRF), Rate Limit and Score Plausibility. Updated 2026-11-15: Microsoft sign-in was removed.

Player Identity: an Id and Three Initials

In plain English: The browser sends its player id and initials with every request. The server turns them into one player identity that every game reads the same way. The id is a name tag, not a password: it keeps one browser's scores apart from another's and proves nothing more.

3Read in one place

UsePlayerIdentity accepts ids of 1-64 letters, digits, - or _ and keeps only three letters of initials. RequestIdentity.Resolve is how every slice reads the caller, so a score's name comes from the caller, never from the request body.

4What it does not do

Anyone can send any id. Scores stay honest through the plausibility checks and server replays below, not through identity.

Permissions, CSRF & Refusals

In plain English: Anyone can read public leaderboards. A state-changing API call needs a matching anti-forgery token so other websites cannot submit actions on your behalf. There is no route-level login gate; an endpoint that needs a player id (cloud saves, ladder progress, a lobby seat) checks for one itself.

Rate Limiting & Score Integrity

In plain English: Rate limits stop automated floods by giving each player+IP pair its own bucket, while the Score Guard blocks impossible numbers (like int.MaxValue) and tracks signed play-session durations.
