Authentication & security

Who are you, and may you do that?

There is no login, on purpose. A player is a random id and three initials kept in their own browser. The server's job is narrower than usual: make sure nobody posts under someone else's id, nobody tricks a browser into posting, and nobody floods the boards.

How a player is recognised

In plain wordsYou wear a name sticker (your id and initials) on every request. The first time, the server also gives you a stamped wristband (a signed cookie) carrying the same id. From then on, a sticker that does not match the wristband is ignored.
  1. Browser makes an idA random id plus your initials, saved in localStorage.
  2. Every call carries themAs X-Player-Id and X-Player-Initials headers; live hubs use playerId and initials in the address.
  3. Wristband issuedWhen the app fetches its anti-forgery token, the server sets an HttpOnly cookie that binds your id, signed so it cannot be edited.
  4. Mismatch is refusedA request showing a different id than the cookie gets no identity at all, and the token endpoint answers 401.

Stopping forged writes

In plain wordsAnother website could try to make your browser post a score for you. To write anything, a request must carry a token in a header and a matching cookie. A foreign page can never produce both.
  1. Fetch a tokenGET /api/auth/antiforgery-token returns the header token and sets the cookie. It is never cached.
  2. Send it on every writePOST, PUT, PATCH and DELETE under /api need X-CSRF-TOKEN.
  3. Stale token? Refresh onceA 403 with antiforgery_validation_failed makes the app fetch a new token and replay the request one time.

Score integrity

In plain wordsTwo checks. First: is this number even possible in this game? That one always applies. Second: could you have scored it in the time since your ticket was punched? That one is in "watch and log" mode until the owner switches it to "refuse".
