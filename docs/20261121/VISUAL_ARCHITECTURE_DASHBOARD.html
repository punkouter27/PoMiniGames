Architecture

How the pieces fit

One server program does three jobs: it hands the browser the game app, answers API calls, and runs live matches. Everything it must remember goes into Azure storage; everything it may forget lives in its own memory.

Runs in the player's browser Runs on the App Service Stored in Azure Outside service

Containers (C4 level 2)

In plain wordsThink of a shop: the browser is the customer's table, the App Service is the counter and kitchen, Azure storage is the filing cabinet in the back, and a few outside suppliers deliver extras.

Core transactions

In plain wordsTwo exchanges matter most: posting a score (one request, checked twice) and an online turn (a move goes to the dealer, who tells both players).
Architecture view: posting a score

  participant MW as Middleware
  participant EP as Score endpoint
  participant G as ScoreIntegrityGuard
  participant S as StorageService
  C->>MW: POST /api/pomule/highscores
  MW->>MW: identity claims from X-Player-Id
  MW->>MW: rate limit (highscores, 10 per min)
  MW->>MW: anti-forgery header vs cookie
  MW->>EP: request
  EP->>G: Inspect(game, score)
  G->>G: tier 1 absolute range (always)
  G->>G: tier 2 session + rate (mode Observe)
  G-->>EP: verdict
  EP->>S: upsert row
  S-->>EP: ok
  EP-->>C: 200 with rank

Stored data

In plain wordsThe filing cabinet has one drawer per board. Each card in a drawer is filed under a folder name (partition key) and a card number (row key). There is no SQL database and no Entity Framework.
